# Zeebe 8.5.23 Downgrade Runbook

Status: prepared 2026-04-29. **Historical — kept for reference only
(ADR-2607071500, 2026-07-07).** The Vultr Kubernetes cluster this broker and
PVC ran on was permanently deleted 2026-06-24/25 (see
`DECOMMISSION-RUNBOOK.md` in this directory and ADR-2607071500), so none of
the `kubectl`/PVC steps below are executable anymore. The file is retained
because `00-contracts/deps.edn` and `30-graph/deps.edn` knowledge entries
reference it by path to document the Camunda-8.6+-licensing / hazelcast
exporter incompatibility decision it recorded.

## Decision

Do not perform an in-place downgrade of the live `mitama-udf/zeebe` broker from
`camunda/zeebe:8.6.39` to `camunda/zeebe:8.5.23`.

The live PVC currently contains broker data under:

```text
/usr/local/zeebe/data/raft-partition/partitions/1
/usr/local/zeebe/data/raft-partition/partitions/2
/usr/local/zeebe/data/raft-partition/partitions/3
/usr/local/zeebe/data/raft-partition/partitions/4
/usr/local/zeebe/data/raft-partition/partitions/5
/usr/local/zeebe/data/raft-partition/partitions/6
```

The repo manifest now declares a single-partition 8.5.23 broker. Reusing the
existing 8.6 PVC risks version and partition-layout incompatibility. The safe
path is a fresh broker state with the old PVC retained for rollback/evidence.

## Preconditions

- Accept loss of in-flight Zeebe process state, or drain externally before the
  cutover.
- Keep Kotoba/Datomic graph state as the durable business record. This procedure
  only replaces Zeebe broker runtime state.
- Confirm no Kubernetes `VolumeSnapshot` CRD is available in this cluster. If a
  storage snapshot facility is later installed, snapshot `data-zeebe-0` before
  step 4.

## Procedure

1. Stop new external starts.

```sh
kubectl -n mitama-udf scale deploy/bpmn-dispatcher --replicas=0
kubectl -n mitama-udf patch cronjob shinshi-melina-pipeline -p '{"spec":{"suspend":true}}'
```

2. Stop Zeebe workers so no jobs are activated during broker replacement.

```sh
kubectl -n mitama-udf scale deploy/zeebe-worker --replicas=0
kubectl -n mitama-udf scale deploy/open-jpn-mynumber-zeebe-worker --replicas=0
kubectl -n mitama-udf scale deploy/pd-color-zeebe-worker --replicas=0
kubectl -n yoro-actors scale deploy/yoro-actor-zeebe-worker --replicas=0
kubectl -n yoro-actors scale deploy/yoro-vector-embedding-worker --replicas=0
kubectl -n shinka-actors scale deploy/shinka-actor-zeebe-worker --replicas=0
kubectl -n intel scale deploy/intel-pyzeebe-worker --replicas=0
```

3. Retain the current PVC and stop the broker.

```sh
kubectl -n mitama-udf scale statefulset/zeebe --replicas=0
kubectl -n mitama-udf wait --for=delete pod/zeebe-0 --timeout=180s
```

4. Preserve the old PVC and create a fresh one.

```sh
kubectl -n mitama-udf patch pvc data-zeebe-0 \
  -p '{"metadata":{"labels":{"etzhayyim.com/retained-before-zeebe-85":"2026-04-29"}}}'
kubectl -n mitama-udf delete pvc data-zeebe-0
```

The backing PV reclaim policy should retain the old Vultr volume. Confirm before
continuing:

```sh
kubectl get pv | rg 'data-zeebe-0|Released|pvc-'
```

5. Apply the 8.5.23 manifest and start the broker.

```sh
kubectl apply -f 50-infra/vultr/zeebe/zeebe.yaml
kubectl -n mitama-udf scale statefulset/zeebe --replicas=1
kubectl -n mitama-udf rollout status statefulset/zeebe --timeout=300s
kubectl -n mitama-udf get pod zeebe-0 -o jsonpath='{.spec.containers[0].image}{"\n"}'
```

Expected image:

```text
camunda/zeebe:8.5.23
```

6. Restart workers and dispatcher.

```sh
kubectl -n mitama-udf scale deploy/zeebe-worker --replicas=1
kubectl -n mitama-udf scale deploy/open-jpn-mynumber-zeebe-worker --replicas=1
kubectl -n mitama-udf scale deploy/pd-color-zeebe-worker --replicas=1
kubectl -n yoro-actors scale deploy/yoro-actor-zeebe-worker --replicas=1
kubectl -n yoro-actors scale deploy/yoro-vector-embedding-worker --replicas=1
kubectl -n shinka-actors scale deploy/shinka-actor-zeebe-worker --replicas=1
kubectl -n intel scale deploy/intel-pyzeebe-worker --replicas=1
kubectl -n mitama-udf scale deploy/bpmn-dispatcher --replicas=1
kubectl -n mitama-udf patch cronjob shinshi-melina-pipeline -p '{"spec":{"suspend":false}}'
```

7. Redeploy BPMN definitions.

The fresh broker has no deployed process definitions. Re-run the existing F5
watcher/deployment sync path, or restart `bpmn-dispatcher` after confirming it
deploys every active `vertex_bpmn_process_def` row.

## Rollback

If 8.5.23 fails to start cleanly:

1. Scale dispatcher/workers back to zero.
2. Scale `statefulset/zeebe` to zero.
3. Restore the old retained Vultr volume as `data-zeebe-0`, or create a new
   PVC bound to the retained PV if Kubernetes still has it.
4. Reapply the previous `camunda/zeebe:8.6.39` manifest.
5. Start broker, workers, then dispatcher.

Do not delete the retained old volume until the 8.5 broker has run cleanly
through at least one full timer cadence and process deployment cycle.
