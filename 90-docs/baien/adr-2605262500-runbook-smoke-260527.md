## USDA SHA observation

Dry-run (`assemble_diagnose dry-run`) and real assemble
(`assemble-usd-scene.py`) produced **identical** usda_sha256 prefix
`c76f6c7fb402…`. This confirms G6 determinism invariant — dry-run is a
faithful preview of the production output bytes.

## Subtle behaviors confirmed

1. **Preflight FAIL on no FACE_MODEL is operator-friendly**, not a runbook
   bug. The printed "operator action items" guide the operator to the
   per-tool diagnostics, which then point at the env-var fix.

2. **assemble_diagnose runs standalone** (no e7m-dataset on PYTHONPATH)
   and correctly falls back to the `stub-no-e7m-dataset` charter scope.
   Operators who want the full Charter scan integration should set
   `PYTHONPATH=70-tools/e7m-dataset/src` when running the diagnostics —
   but production assemble does NOT depend on this (it uses the same
   defensive fallback).

3. **G11 eval scalar mode** is a smooth on-ramp for operators who
   already have Isaac Sim metrics from an external test run — no need
   to wire up image/point-cloud files yet.

## What this smoke does NOT cover

Operations requiring operator-side env that this smoke can't validate:

- `e7m-dataset pull mapillary --token $MAPILLARY_TOKEN` (needs real Mapillary token)
- Real ONNX face-detector smoke (`vision_pii_diagnose smoke`) needs an actual model file
- `pds_diagnose resolve` against live `pds.etzhayyim.com` (needs network + real datasetPin record)
- W2.4 rasterio path (needs `pip install rasterio`)

These are all "operator-side env prep" that the runbook directs the
operator to set up. The runbook smoke confirms the **paths that
should work without operator setup actually do work**.

## Recommendation

Runbook is **production-ready as written**. No content changes needed
from this smoke. One small operator-side hint that could be added (but
isn't blocking): mention `PYTHONPATH=70-tools/e7m-dataset/src` when
running e7m-sim diagnostics if the operator wants the full Charter
scan integration (vs the defensive stub fallback).
