## What the reverts probably meant

The agent didn't get an explicit explanation, but the consistent pattern
suggests user intent:

- **Keep**: governance docs (ADRs, surveys, runbooks, checklists),
  cross-repo amendments (vendor `deps.toml` + vendor ADR-2605212100 §2
  STATUS blocks), file-relocate operations (3 lg subtrees + 1 hume inline),
  status snapshots, closure confirmations.
- **Revert**: per-worker Python implementation code (the ~37 files in
  `kotodama/` + 4 substrate primitives + 4 ingest modules).

Possible reasons (agent's best guess; not confirmed):

1. The per-worker ports may have had subtle bugs the agent didn't catch
   in smoke tests (e.g. wrong column order, missing index, async/sync
   confusion).
2. The user may prefer to land per-worker ports as separate PRs with code
   review rather than as session-internal bulk commits.
3. The user may have a different implementation strategy in mind for some
   workers and didn't want the agent's prototype to set precedent.
4. The user may want the operational/governance work to land first (which
   it did) and the code execution to happen in a more controlled context.

In any case, the **gate (a) execution checklist** (`90-docs/2605211949-...`)
is the agent's contribution toward making future per-worker port attempts
more checkbox-trackable, regardless of who/when actually executes them.

## Lessons for future sessions

1. **The reverts are not noise**. When the user issues many small reverts in
   a row, the right move is to (a) audit disk state, (b) update docs to match
   that reality, (c) ask for clarification on which artifacts they want.
2. **Governance work landed; code execution didn't**. This is a valid mid-state
   — runbooks without execution are still useful (they make the next attempt
   faster + more correct).
3. **The gate (a) checklist** is the single most actionable artifact for the
   next session/operator. 42 rows × ~15 minutes per row = ~10 hours of
   focused per-worker port work + smoke tests.
